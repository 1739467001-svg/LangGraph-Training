## 一、逐站对照（tech-spec 3.2 的每一站 ↔ 课程里验证过的实现）

| tech-spec 节点 | medrecord 对应 | 状态 | 备注 |
|---|---|---|---|
| normalize 整理证据时间线 | `load_orders`（医嘱+检查联表） | **部分** | 真实设计是「统一证据模型」（检验#1/录音#4），medrecord 是按表分别读——移植时要做证据时间线抽象 |
| privacy_gate 出口闸门 | `privacy_gate.py`（第 16 课原型） | **已有原型** | 两道闸已实现（流程开头 + 每次调模型前），词表从脱敏映射表自动装载；移植到真实仓库时接入 `pipelines/privacy_gate.py` |
| compute 代码计算 | 第 2 课排序/第 4 课归一化 | 部分 | 住院天数、体温极值等专项计算未做（medrecord 场景不需要） |
| extract_section 按栏目并行 | `dispatch` Send 多态分发 | **已验证** | 两种工位（模型/代码）混合派发，比真实设计多了「不是所有栏目都要模型」的实践 |
| verify 逐字核对 | `verify_all`（双分支闸门） | **已验证** | 我们的出处是「表+行号」；真实设计是 claim+quote（原话逐字）——quote 更通用，应采纳 |
| write 成文节点 | **没有**（草稿由代码拼装） | **缺失** | 真实设计是第二个 LLM 节点（书记员），只准用核对过的事实成句——第二大缺口 |
| qc 质控回路 | 第 2 课 qc_check + 第 13 课重试 | **已验证** | 语义一致：不通过退回重写，最多 2 次。真实设计退回的是 write（成文），我们退回的是 extract |
| review 医生审核 | `doctor_review`（interrupt/Command） | **已验证** | 含 SqliteSaver 跨进程「医生第二天审」——tech-spec 未提及，可作为增强项反哺 |
| render 排版 | `export_eval`（XML 两栏目） | 部分 | 真实设计渲染 MD + 录音时间段回放链接 |

## 三、真实仓库独有的、课程没覆盖的（移植时要学的新东西）

1. **出口闸门（privacy_gate）**：两道（流程开头 + 每次调模型前），报警信息自身也打码。
   → 可用 deid_tools 的手机号/身份证/长编号正则做检测器，但必须**补代码**。
2. **成文节点（write）+ 质控反馈**：LLM 只准用核对过的事实成句，qc 把「没有出处的句子」
   打回去。→ `src/prompts/write_section.v1.md` 已备好提示词，节点待写。
3. **证据时间线统一模型**：录音/检验/检查/医嘱全部整理成带编号的 events，
   出处从「表+行」升级为「证据编号」。→ normalize.py 是数据工程的主战场。
4. **拟行 ≠ 已行**：医嘱「拟行手术」不得写成「已行」——课程提示词里有这条规则，
   但没有专门的核对分支（真实仓库有 `test_plan_is_not_written_as_done`）。
5. **口语数字换算提示**：门诊线专属（「三十八度二」→ 38.2℃ 且 quote 保留原话）。
6. **提示词版本管理**：v1/v2 药方规则（改提示词必建新版、写明改了什么/为什么/用哪组样例测过）。
   → 课程里提示词是代码字符串，移植时按仓库规范外置成 `src/prompts/*.vN.md`。

## 五、课程实践可直接回答的真实仓库待确认问题

| OPEN-QUESTIONS | 我们的实践给出的参考答案 |
|---|---|
| Q-B1 结构体检 | `deid_tools/inspect_structure.py`（脱敏前打码版）与 `gen_structure_report.py`（脱敏后版）已成对；注意真实仓库要求**在原始数据上人工逐行检查**——我们的经验：先做「值打码」检查脚本，能把人工检查的风险降到最低 |
| Q-B2 对照答案有哪些 | 5 位患者 zip 内共有**用药记录 28 份**（甲 6 / 丙 10 / 丁 4 / 戊 5 / 乙 3）等文书可做对照答案；建议据此定 Q-A1 的 Demo 文书范围（用药记录数据链最全） |
| Q-B6 脱敏怎么验证 | 反向搜索校验 + 完整性核对的两条验收线（第 0 课），可直接写进 data-spec 的脱敏规范 |
| Q-B4 主诉/现病史无来源 | 检查所见工位证明了分工：**有结构化来源的栏目用代码，无来源的栏目代码统一加「待医生补充」**——不要让模型硬写（与 tech-spec 原则 4 一致，已有实测数据支撑） |
| Q-E2 验收标准 | 三指标（覆盖率/多报/编造）+「未覆盖原因必须随数字汇报」的句式，可作为验收讨论的底稿；甲患者实测：基线覆盖率 80%，缺口在麻醉数据源 |
